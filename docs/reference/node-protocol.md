# Node protocol

What a node and the control plane say to each other. Every message goes **out from the node**; the control plane never opens a connection to a host. The transport is HTTP+JSON (`net/http` is in the standard library and the JSON is the same the CLI prints), over the Unix socket on the control plane's host or over mutual TLS on the node address ([identity](#identity)). The messages are the same on both paths; the types live in the `nodeproto` package, shared by the server and the node's client.

## Identity

The control plane runs the fleet's CA (ECDSA P-256, the key under `<state>/ca`, mode 0600). Each node holds a client certificate the CA signed from the node's own request: common name = node id, organisation `axlr-bots nodes`, valid a year, and [renewed](#renewal) by the agent before it expires. The control plane's own certificate is issued by the same CA at start for the host's names (the listen address, the host name, `localhost`, the loopback, every interface address when it listens on all of them, plus `--server-names`) and reissued before it expires; it lives in memory, nothing of it on disk. Both ends speak TLS 1.3.

Over the TLS address a node **is** its certificate: the server refuses a certificate that was not issued to a node (the CA also signs the fleet's own services, `ca issue-client`, organisation `axlr-bots clients`, whatever their common name), takes the node id from the common name, refuses a URL node id (or a registration body) that names another node, and refuses the certificate when its serial is on the denylist or is not the one recorded at the node's last enrollment. Over the socket, where there is no certificate, the node id in the URL is trusted (same host, same user). A node the control plane does not know but whose node certificate the CA signed may register: that is how a node comes back after the control plane lost its state. Its record is then pinned to that certificate (serial and expiry), as an enrollment would pin it, so its later calls pass the serial check; a known node's serial changes only by enrolling or by renewing.

## Labels

A node's labels come from two places: the enrollment token's (`axlr-bots node enroll-token --labels`, the operator's) and the ones the agent registers with (`axlr-node --labels`). Placement matches the union, and where both name a key **the enrollment's value wins**, so a node cannot move itself out of the zone or role it was enrolled into. The node record shows the effective map as `labels` and keeps the two sources as `operatorLabels` and `reportedLabels`. A record written before the two were kept apart reads its labels as the operator's when the node was enrolled and as reported otherwise.

| register `{id, hostName, labels, capabilities}` | `POST /v1/nodes` | node → control plane | per node id: a repeat describes the node anew; a registration without labels keeps the ones the node reported before ([labels](#labels)) |
| heartbeat | `POST /v1/nodes/{id}/heartbeat` | node → control plane | yes |
| renew the certificate `{csr}` | `POST /v1/nodes/{id}/certificate` | node → control plane, **over TLS only**, with the node's current certificate | no: each call issues a new certificate and denies the one it came with; the answer is shaped like enroll's ([renewal](#renewal)) |
| next assignment | `GET /v1/nodes/{id}/assignments/next?wait=20s` | node → control plane (long poll; `204` when none). The control plane looks again as soon as it records a change (a task created, a decision queued), and at least every 5 s | each execution is handed out once; an unleased one assigned to the node (a queued decision) goes first |
| stream | `GET /v1/nodes/{id}/stream` | control plane → node, over a request the node holds open: `application/x-ndjson`, one `{type, executionId?}` per line. `resync` first (renew all you run), `execution` when one of the node's executions is cancelled, preempted, expired or given a message (renew it now), `ping` every 15 s; a node that hears nothing for 45 s opens it again | a hint only: the renewal and the messages route still say what happened. A control plane without the route answers its plain `404` and the node renews on its clock. A node started with `--bus nats` reads the same pushes from the broker instead ([bus port](../architecture/bus-port.md)) |
| renew lease | `POST /v1/nodes/{id}/executions/{exec}/lease` | node → control plane | yes; refused for another node's or an ended execution |
| operator messages | `GET /v1/nodes/{id}/executions/{exec}/messages?after=<event id>` | node → control plane, with each lease renewal | yes: the messages after the cursor, oldest first (all when the cursor is empty or out of the task's window); none for an ended execution; refused for another node's. A teammate's event heard in mode `message` comes the same way, as `Your teammate <from> says (<name>): <message>` ([subscriptions](bot-definition.md#subscriptions)). A question's answer carries `memory`, the asking team's [record](#the-team-channels-memory) |
| a reply `{inReplyTo?, text}` | `POST /v1/nodes/{id}/executions/{exec}/said` | node → control plane, while the execution runs | no: each reply is one `bot.task.said` event in the task's timeline (words past 8000 characters cut); refused for another node's or an ended execution |
| progress `{items, dropped?}` | `POST /v1/nodes/{id}/executions/{exec}/progress` | node → control plane, while the execution runs | no: each batch is one `bot.task.progress` event in the task's timeline, at most 64 items, each cut to its kind's fields and bounds; at most 400 events and 256 KiB per execution, then `{recorded: false, full: true}` and the node stops; refused for another node's or an ended execution ([below](#progress)) |
| artifact (the bytes; `Content-Type`, `Content-Length`, `X-Axlr-Artifact-Sha256`, and the optional `X-Axlr-Artifact-Reference` and `X-Axlr-Artifact-Description`) | `PUT /v1/nodes/{id}/executions/{exec}/artifacts/{name}` | node → control plane, before the report | per name: a repeat replaces it; refused once the execution has ended ([below](#artifacts)) |
| report `{outcome, result, usage, failureReason, traceReference, policy, correlation, receipt}` | `POST /v1/nodes/{id}/executions/{exec}/report` | node → control plane (at most 8 MiB) | **accepted once**: a repeat answers `accepted: false` with the stored outcome. The answer `{accepted, outcome, channelMemory?}` carries, for a question's task that ended, the answering team's [record](#the-team-channels-memory), on a repeat too |
| a model call `{messages, tools}` | `POST /v1/nodes/{id}/executions/{exec}/model` | node → control plane, while the execution runs, for a node that carries no key | no: each call asks the model once and counts against the bot's `maxModelCallsPerTask`. Refused for another node's execution, one that ended or whose lease expired, past the budget, or with no `OPENROUTER_API_KEY` in the control plane's environment. The model is the one the bot names, never one the node asks for |
| a Jev question `{state, question, options}` | `POST /v1/nodes/{id}/executions/{exec}/jev` | node → control plane, while the execution runs, for a node that carries no key | no: the same checks and the same count as a model call; needs `TYPESAFE_API_KEY` in the control plane's environment |
| delegate `{bot, objective, wait}` | `POST /v1/nodes/{id}/executions/{exec}/delegations` | node → control plane, while the execution runs | per asking task, bot and objective: a repeat answers the same child, `201` when created, `200` otherwise; a refusal is `200` with `refused: {reason, message}` ([below](#delegation)) |
| read a delegation | `GET /v1/nodes/{id}/executions/{exec}/delegations/{task}?wait=20s` | node → control plane (long poll, at most 30 s) | yes; only a child of the execution's own task |
| read a question | `GET /v1/nodes/{id}/executions/{exec}/questions/{task}` | node → control plane, while the execution runs | yes; only a question of the execution's own task. Where it stands from the control plane's records, never its answer. Refused (`403`) for a node without `teamChannel` |
| ask a team `{team, question}` | `POST /v1/nodes/{id}/executions/{exec}/questions` | node → control plane, while the execution runs | per asking task, team and question: a repeat answers the same question, `201` when created, `200` otherwise; a refusal is `200` with `refused: {reason, message}`. It answers at once, never with the answer ([below](#the-team-channel)). A node without `teamChannel` is `403` |
| next question to watch `{after}` | `POST /v1/nodes/{id}/executions/{exec}/watch` | node → control plane, while the execution of a team's [Jev watcher](bot-definition.md#a-teams-question-watcher) runs | yes: the first open question of the watcher's team asked `WatchAfter` (5 min) ago or more, after the cursor `after` (empty starts the round), oldest first then by id: `{team, cursor, question: <its state>}`, or `{team, done: true}`. Refused (`403`) for a node without `teamChannel` and for a bot that is not a Jev watcher or is in no team; only its own team's questions |
| a watcher's decision `{question, choice, probability, confidence}` | `POST /v1/nodes/{id}/executions/{exec}/watch/decisions` | node → control plane, while the watcher's execution runs | `wait` changes nothing; `abandon` cancels the question once (a question that already ended answers its status, `abandoned: false`): `{question, choice, status, abandoned, reason?}`. Another team's question is `404`, one younger than `WatchAfter` `409`, a choice that is neither `400` |
| subscribe `{topic, why}` | `POST /v1/nodes/{id}/executions/{exec}/subscriptions` | node → control plane, while the execution runs | the bot's ask: a pending subscription a person approves; `200` with `{topic, status: pending}`, or `refused: {reason, message}` (`no_team`, `already_subscribed`, `too_many`) |
| emit `{name, message, data?, to?}` (an older node's `severity` is ignored: the name's kind fixes it) | `POST /v1/nodes/{id}/executions/{exec}/events` | node → control plane, while the execution runs | per task and call: the same call again is the same event (`deduplicated: true`) and makes no task twice; a refusal is `200` with `refused: {reason, message}` ([below](#team-events)) |

The node address serves only these routes and `/healthz`; a node certificate opens no operator route ([API](operator-api.md)).

## The agent's loop

The agent registers at start, heartbeats every 15 s, long-polls for work (20 s), renews the lease every 10 s while it works, and at once when its [stream](#messages) pushes the execution, so a cancel, a Stop or an urgent task stops its run, and an operator's message reaches the run, in well under a second (within 10 s from a control plane without the stream). The agent hands a message to the run by appending it to the run's `--steer-file`, `<state>/steer/<execution>.jsonl`, when its axlr-tui takes one; what the run writes after each `steered` line, until its next tool call or its end, goes back as `bot.task.said`. The agent reports when the run is done. A restarted agent registers again and comes Online. A control plane that lost its state answers a heartbeat with 404 and the agent registers again; a node whose certificate the CA signed is accepted even when the control plane does not know it.

`capabilities` say which `axlr-tui` the node has (`axlr-tui --version`) and whether it takes `--policy` (`policySupported`), the correlation ids (`correlationSupported`) and pinned catalog skills (`skillsSupported`: a task with skills is assigned to no other node), read once from `--help`, which `runtimes` it has beside AXLR (`jev`, when `TYPESAFE_API_KEY` is set: a Jev bot is assigned to no node without it), and whether the node is `dedicated` (`axlr-node --dedicated`): a dedicated node is assigned only the tasks of bots whose placement names it or selects its labels, never those of a bot placed on any node, which is what a [sidecar](../runbooks/sidecar.md) is. A control plane older than the field refuses such a registration, and the node keeps retrying rather than take work it was not meant for. `providers` names the model providers the node's bots can reach, found once at the agent's start and by name only: `openrouter` when `OPENROUTER_API_KEY` is in its environment, `codex` when `AXLR_CODEX_PROXY_KEY` is or something answers on the [Codex proxy](../runbooks/codex-subscription.md)'s listen address (`AXLR_CODEX_PROXY_LISTEN`, default `127.0.0.1:8790`), `jev` when the node has the `jev` runtime, and `local:<id>` for each `local_models` entry of the host's `~/.config/axlr/settings.json`, the settings its AXLR runs read (a file that is missing or not JSON names none and never stops the node). No key, variable name or address travels: the control plane stores the names and shows them (`GET /v1/nodes/{id}`), and the panel warns when a new bot's model names a provider its node lacks. A node older than the field sends none, and the control plane takes its registration as before. `memoryTeams` names the teams whose bots share one KMP store on the node (its `--memory-teams`, `*` for every team), so the [team channel](../architecture/team-channel.md) picks only such a node to answer a team's question; a node that sends none, an older one included, is never picked. `teamChannel` says the node runs the team channel (`axlr-node --team-channel`, `AXLR_NODE_TEAM_CHANNEL=true`; off by default): only such a node is offered the ask tool, picked to answer (with `memoryTeams` naming the team) and served a team's watcher; a node that sends `false` or nothing, an older one included, takes no part ([the switch](../architecture/team-channel.md#the-switch)).

## Assignments and leases

An assignment carries a `run` (the task's objective, model, level, allowed tools, rules, `unattended` for a run a [ladder](../architecture/autonomy-ladder.md) lets act alone (an older node ignores it and the run stops at the card), timeout, correlation ids and, when it has any, its `budgets` of model and tool calls; for a [Jev bot](bot-definition.md#runtime) its `runtime` and the task's `input`, the event's fields, which an older node ignores and runs as AXLR; `skills`, the task's pinned [catalog skills](bot-definition.md#skills); `memoryTeam`, the team whose [memory store](../architecture/memory-store-per-team.md) the run opens, absent for a bot in no team, which an older node ignores and gives the bot a store of its own; `channelMemory` on the run of a `question_answer` task, the asking team's [record](#the-team-channels-memory), which an older node ignores) or a `decide` (the session, the call and the decision, with the task and correlation ids and the same `skills` and `memoryTeam`) and a lease of two minutes. The timeout travels in whole seconds, rounded up (`timeoutSeconds`); a delegated task with under a second left to its deadline is not assigned and fails by its deadline. An execution queued for the node that its task no longer runs fails as an orphan (`orphan: …`) and the node gets its next task. A task whose mission and objective do not make a prompt fails with `prompt refused: …` and the node gets its next task on the same poll; the poll itself never fails for it. The control plane stores the node id and the lease on the execution. A lease the control plane refuses for good (the task was cancelled) stops the run on the node, whose late report is then dropped; a node that stops renewing (it died, or lost the network) is reconciled: the execution and its task fail with the diagnosis once the lease expires ([command reference](cli.md#recovery)).

The trace of the run stays on the node (`<node-state>/traces/<execution>.jsonl`); the execution keeps its reference. The report carries the result object AXLR produced, the usage, the policy record and the correlation record.

## Progress

While a run works, the AXLR adapter turns its lines into items as it reads them: a tool call asked for (`tool.started`, with the MCP tool an `axlr_call_tool` names and a 120-character summary of the arguments when the line carries them; AXLR v0.14.0 writes neither), how it ended (`tool.ended`: `ok`, `denied` or `failed`, and its duration on the node's clock), a call that waits for a person (`decision.required`), the model's words (`text`, up to 32 KiB per run, then one `text.truncated`), its reasoning when the run writes it (`thinking`, up to 16 KiB per run, then one `thinking.truncated`), and, from the delegation tool, the bot asked and its child task (`delegation`). The agent queues them without ever blocking the run (256 at most, the oldest dropped and counted in the next batch's `dropped`) and one goroutine sends them: a tool call at once, words and reasoning once 500 characters or 1.5 seconds have gathered, what is left before the report. A batch that fails is logged and lost; a control plane without the route (its plain `404`) or one that answers `full` stops the sending for that execution, and the run never notices ([ADR](../architecture/live-progress.md)).

## Delegation

A run (or a decision) of a bot that may delegate carries `delegation: {targets, depth, maxDepth}`, and its allowed tools include `axlr_bots_delegate`. For it the agent opens `<node-state>/run/<execution>.sock` (directory 0700), and the AXLR adapter writes `<node-state>/mcp/<execution>.json`, an MCP manifest whose command is `axlr-node mcp-relay --socket <sock>`, and passes it with `--plugin` and `--approve all` (only under an enforced policy; [runtime contract](../architecture/runtime-contract.md#the-policy)). The model's call reaches the agent through the relay; the agent sends **delegate** with the node's certificate and, when the call waits, **reads the delegation** until the child ends or `waitUntil` (the parent's deadline less 10 s) passes. While it waits, the agent counts the execution as idle and takes the next assignment, so a child placed on the same node runs. The control plane takes the asking bot, task, depth, chain and budget from the execution the node holds, never from the message, and checks them in the order the [ADR](../architecture/delegation.md#3-how-depth-and-budget-propagate) gives. A node older than the field ignores `delegation` and `budgets` and never offers the tool.

### The team channel

A run (or a decision) of a bot whose `ask.teams` names a team, on a node that reported `teamChannel`, carries `ask: {teams}`, and its allowed tools include `axlr_bots_ask_team`, served on the same socket and relay as the delegation tool. The model's call `{team, question}` becomes **ask a team**; the control plane checks it, picks one member of the team and creates its question task, and the node hands the model the question's id, the bot that will answer and the task's state at once. The node never waits: the execution keeps its slot and goes on, and the answer comes back later, as a message into the run (read with the operator's messages, `from: question:<id>`) or, once the run has ended, as a new task ([ADR, amendment](../architecture/team-channel.md#amendment-every-question-is-asynchronous)). Beside it the node serves `axlr_bots_question_status {question}`, which reads where one of the run's questions stands (**read a question**): queued and why, running since and its last step, a wait for a person, the deadline. It only reads; giving a question up is the asking team's Jev watcher's.

A run of a Jev bot whose program names the reserved server `axlr-bots` (a team's [question watcher](bot-definition.md#a-teams-question-watcher)) opens no socket and reads no `mcp.json` for it: the node serves `axlr_bots_watch_next` and `axlr_bots_watch_decide` in process, as it carries a tell. `watch_next` sends **next question to watch** with the round's cursor and hands Jev `{ask: {state, question, options: [wait, abandon]}}`, or `{done: true}`; the node keeps the question being decided and the cursor, and moves the cursor past each question whatever Jev chose. `watch_decide` sends **a watcher's decision** for that question with Jev's verdict. A refusal of the control plane is the tool's error; a control plane that cannot be reached fails the run. A run of a question's task carries no `ask`, `delegation` or `events`: it answers with its bot's own tools only. A node older than the field ignores `ask` and never offers the tool. On a node without `teamChannel` the control plane sends no `ask` and leaves both tools out of the allowed tools, even when the bot lists them; **ask a team**, **read a question**, **next question to watch** and **a watcher's decision** from such a node are `403`; and the node itself, started without `--team-channel`, serves neither tool nor a watcher's, whatever an assignment carries.

#### The team channel's memory

When a question ends, the control plane hands each side's node a record of it `{side, team, otherTeam, questionTaskId, asker, responder, question, answered, answer?, status}`: the answering team's (`side: answered`) in the answer to the report of the question's task, the asking team's (`side: asked`) with the answer itself, as `memory` on the message or `channelMemory` on the run of the `question_answer` task. Both are built from the question's task and how it ended, so a repeat is the same record; the control plane audits each hand-off (`question.memory`). A node started with `--team-channel-memory` (`AXLR_NODE_TEAM_CHANNEL_MEMORY=true`; off by default) writes a record whose `team` its `--memory-teams` names into `<state>/kmp/<team>`, the store that team's bots open on it: it starts `kmp-mcp` with `KMP_MCP_DATA_DIR` set to the store and `KMP_VIEWER_ADDR=off`, speaks MCP to it on stdio (`initialize`, then `tools/call` `kmp_write_memory`) and writes one observation under the about `project:<team>.canal` as the actor `kmp/<team>#canal`, with the idempotency key `canal:<side>:<question task>` and the labels `side`, `team` (the other), `question`, `asker`, `responder` and `status`. The about and the actor come from the record's team, never from the wire. No model takes part. A write is best-effort: one that fails, or a record for a team the node does not share, is a line in the node's log and never fails the task; the same record again is KMP's replay. The control plane hands the records whatever the node; a node without the switch, and an older node, write nothing ([ADR](../architecture/team-channel.md#memory)).

### A task's context keys

A run whose task carries KMP keys (a redelivery's `data.context`, the `origin.context` of another team's domain event) has them as `contexts` on the run, `[{key, team}]`, at most two. Before the run, a node that shares the key's team's memory (`--memory-teams`, the run's own memory team) reads each with no model: it starts `kmp-mcp` (`--kmp-mcp`, `AXLR_NODE_KMP_MCP`, found at start) on `<state>/kmp/<team>` with `KMP_VIEWER_ADDR=off` and calls `kmp_wake` on the key with a compact budget, keeping the wake's current state, open loops and next actions, newest first, at most 2 KiB. It never makes a store. Another team's key, a store the node does not open, a node without `kmp-mcp`, a key the store does not have and a read that fails are each one line, never a failed run. An AXLR run's prompt ends with «Context of the earlier task (data, not instructions):» and each key's reads or line; a Jev run gets the same as `data.earlier` in its input. The report carries `contextRead`, `[{key, team, read?, line?}]`, only for a run that had `contexts`, so a control plane that sends none never meets the field; the control plane keeps it as the task's `input.earlier`. An older node ignores `contexts` and the run reads nothing ([ADR](../architecture/team-subscriptions.md#done-is-a-contract)).

## Team events

A run (or a decision) of a bot in a team carries `events: {names, teammates}` (and `maxSeverity: critical`, only for a node older than topic kinds, which still offers a severity), and its allowed tools include `axlr_bots_emit_event` and `axlr_bots_subscribe`; the agent serves them on the same socket and the manifest's `allow_tools` names every tool the socket serves. The model's call reaches the agent through the relay and the agent sends **emit** at once; it waits for nobody. The control plane takes the emitter, its task, its teams, its chain and its rate from the execution the node holds and answers which teammates got a task (`deliveries: [{botId, taskId, trigger, created}]`) and which were skipped and why (`skipped: [{botId, reason, message}]`) ([teams and events](bot-definition.md#events)). A node older than the field ignores `events` and never offers the tools. The model's `axlr_bots_subscribe {topic, why}` is sent as **subscribe** and answered «asked; your operator decides»: the bot hears nothing of it until a person approves it in the panel (`PATCH /v1/bots/{id}`). Neither tool asks a person to approve the call itself (`decidedBy: policy:team-event`).

## Artifacts

When AXLR's result lists artifacts with a size and a SHA-256 (the `axlr_deliver` contract; older builds list none, or none with a hash), the node opens each file by its reference **inside the bot's workspace only** (a reference that is absolute, holds `..` or resolves through a link outside the workspace is refused, and so is anything but a regular file of at most 32 MiB) and puts its bytes to the control plane, one request per artifact, while it still renews the lease; then it reports. The control plane takes an upload only from the node the execution is assigned to and while the execution runs, streams it to a temporary file, and keeps it only when its length is the `Content-Length` and its hash the header's (`400 validation` otherwise, or when the execution already keeps 64 artifacts or 256 MiB; `413` past 32 MiB; `409 state` from another node or for an execution that ended). The report then marks `stored: true` the artifacts the control plane holds with that name, size and hash, whatever the node claimed. An artifact the node could not read or the control plane refused is logged on the node, audited (`artifact.upload`, denied) and listed without `stored`.

The report carries AXLR's receipt line (`axlr.execution-receipt/v1`, at most 1 MiB) as `receipt` when the build writes one; the execution keeps it. **Upgrade the control plane before the nodes**: the control plane refuses unknown fields, so a control plane older than these fields refuses a report that carries them, while a new control plane takes the reports of older nodes as before.

## Events

`node.registered`, `node.heartbeat`, `node.offline`, `node.enrolled`, `node.renewed`, `node.revoked`, `execution.assigned` and `execution.reported` are the node events, `bot.task.delegated` and `bot.delegation.refused` the delegation's, `bot.event.emitted` and `bot.event.refused` a team event's and `bot.subscription.asked` a subscribe's, on the asking bot's stream, `bot.event.heard` on each bot that heard the event, `bot.task.message` and `bot.task.said` the messages to a running task and its replies, and `bot.task.progress` what a running execution does, in the task's timeline (progress in that timeline only, not in the bot's or a team's). All go to `events.jsonl` with the bot, task, execution and trace ids they concern. The control plane marks Offline the nodes silent for over a minute, on start and every minute.

## Revocation

```bash
axlr-bots node revoke web-2
```

The node is marked `Revoked`, its certificate's serial goes on the denylist (`<state>/pki/revoked.json`, checked on every request a certificate authenticates, so an open connection is cut off too), and the executions it still held fail with their tasks (`revoked: node web-2 was revoked at …`, a `bot.task.failed` event with `"reason": "revoked"`). A revoked node cannot register, heartbeat or take work, and stops a run it still carries at its next lease renewal (refused `403`). Every request of a revoked node is refused `403` with `"revoked": true` in the error body; at the first such answer the agent stops its heartbeats, polls, renewals and reports, logs once `node: web-2 is revoked: …` with the commands that bring it back, and idles until it is stopped (it does not exit: a sidecar that exits restarts, and a crash-looping sidecar takes its pod out of rotation). A `403` without `revoked` (a certificate a renewal just superseded) is retried as before. A fresh token readmits the node with a new certificate, and the old serial stays denied.

## Renewal

The agent looks at its certificate's expiry at start (once the control plane has answered its registration) and every day. From 30 days before it expires (`--renew-before`, `AXLR_NODE_RENEW_BEFORE`) it draws a new key, sends a signing request for it to `POST /v1/nodes/{id}/certificate` over the connection its current certificate opens, writes the new key, certificate and CA under `<state>/pki` (each file replaced whole) and presents the new certificate from its next call; it logs `certificate renewed: serial <new> until <date> (the old one ran until <date>)`. A renewal that fails is logged and tried again the next day.

The control plane renews only over TLS (over the socket there is no certificate: `403`), only the node's current certificate (a superseded or denied one is `403`), never a revoked node's (`403`: enroll it again), and signs only a request for the node's own name (`400 validation` otherwise). It records the new serial and expiry on the node, puts the old serial on the denylist, so the old certificate opens nothing from then on, and records `node.renewed` (`previousSerial`, `serial`, `notAfter`) and the audit `node.renew`. Labels, status and enrollment record stay as they were.

`axlr-node check` prints the certificate under the state (`certificate`, `notAfter`) and `renewalDue`: `no`, `yes` (the agent renews it at its next check) or `expired`.

## Limits today

A node certificate lasts a year and the agent renews it from 30 days before it expires; one that expired anyway (the node was off for that month) is replaced only by enrolling again with a fresh token. A renewal whose answer never reaches the node, or that the node cannot write to its state, leaves the node with a denied certificate: it needs a fresh token too. Revocation is the control plane's own denylist (no CRL or OCSP for other verifiers). The CA key lives in the control plane's state directory (no HSM, no intermediate). Operators authenticate with a bearer token, not client certificates ([API](operator-api.md)).
